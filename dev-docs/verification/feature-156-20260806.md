# Feature #156 — Android justified text alignment

Gate-5 acceptance pass. Four WIs (`android/v0.23.4` → `v0.28.0`), shipped as
**justify-by-default with no new UI control**.

## Production paths, in user words

| Format | Path |
|---|---|
| **TXT / MD** | Library → tap the book → the body text renders with both margins flush (Latin); both margins as before, right edge still ragged (CJK) |
| **EPUB** | Library → tap the book → body paragraphs render flush to both margins (Latin). For line spacing: Library → tap the book → tap centre → bottom bar **Display (Aa)** → Line spacing |
| **AZW3** | Library → tap the book → the body text renders with both margins flush — **no Display control involved or needed** (AZW3 has none; bug #368) |

No new UI was added anywhere. The entire production diff for AZW3 is **one CSS rule plus one inert
comment**.

## The headline result: AZW3 justifies CJK where EPUB cannot

This was the open question Gate 2 asked to be **confirmed rather than assumed**, and the engine
argument held: ReadiumCSS's `cjk-horizontal` stylesheet carries no `USER__textAlign` rule, but that
is a **ReadiumCSS policy** and the foliate path never touches it — AZW3 renders through Chromium
with **our own** injected CSS.

Measured on the real CJK AZW3 (`p.normaltext`, 552 chars, 33 line boxes over 3 columns), production
arm vs a pre-#156 reconstruction injected through the same production `setStyles` seam:

| | Before | After |
|---|---|---|
| computed `text-align` | `start` | **`justify`** (and back on re-injection) |
| column 1, 16 justifiable lines | ragged 1481.48–1492.61, **spread 11.13px** | **1498.98 exactly, spread 0.00px** |
| column 2, 14 justifiable lines | ragged 1864.83–1881.93, **spread 17.10px** | **1882.33 exactly, spread 0.00px** |
| lines moved | — | **30 of 32 right, 0 left** (the 2 non-movers were already within 0.40px) |
| paragraph's final line | — | **0.00px — no stretched last line** |

`body` stays `start` and the `h1` stays `center`, so the blast radius is confined to paragraphs —
**unlike EPUB**, where WI-2 measured headings *inheriting* justification from ReadiumCSS's `:root`
rule (E1c).

**Computed style alone could not have carried this claim.** The book's publisher stylesheet is a
live confounder, so every assertion is a with-rule/without-rule **differential on the same
document**, and the control is derived from the **live** injected blob (selected by a production
ownership sentinel) rather than rebuilt from assumed defaults. A Latin positive control injected
into the same document on the same engine moves **11/11** lines — so a CJK negative would have been
distinguishable from a broken harness.

## A real user-facing defect, inherited from iOS #95 and caught here

`[class*='right']` **also matches `copyright`** — so every `<p class="copyright">` was silently left
ragged. The guard is now a token match plus alignment-shaped patterns, proven in the live DOM:
`copyright → justify`, `align-right`/`alignright → start`, uppercase `TEXT-ALIGN → center`.

This shipped on iOS and was carried into the Android port before Gate 4 caught it.

## Three measurement defects fixed rather than tuned around

Each would have produced a **confidently wrong** number:

1. **A `ComposeTestRule` freezes the Compose clock** outside `waitForIdle`/`waitUntil`, so a
   `Thread.sleep` polling loop starved composition and the reader never rendered.
2. **The first subject paragraph was `<br>`-separated front matter**, where every line is a last
   line — it would have shown computed `justify` with **zero glyphs moved**, indistinguishable from
   a CJK no-op.
3. **Sorting line rects by (top, left) interleaved the CSS columns**, so the collapse figure was
   measuring the 775px column pitch rather than the ragged spread.

## What is NOT covered — stated plainly

1. **The EPUB screenshots show cover art, not body prose.** Neither injected taps nor swipes moved
   the Readium host off its cover, so EPUB's justification evidence is **WI-2's computed-style
   matrix**, not a pixel artefact. AC-4 is a DOM criterion by its own wording, so this does not
   weaken it — but the pixel corroboration I asked for was not obtained for EPUB.
2. **The AZW3 screenshot is the book's opening page**, not body prose (pages past the front matter
   render blank under injected taps; the harness fails loudly rather than saving an empty frame).
   It *does* show visible CJK inter-character stretching. The AZW3 **body-prose** claim rests on the
   DOM measurement.
3. **The guards are heuristics.** A paragraph the book centres via a stylesheet class whose *name*
   contains no alignment word is still force-justified — the real fixture's own `.yingwen` is
   exactly that shape. Verse-as-`<p>` and blockquote inner prose are likewise uncovered, carried
   from iOS #95.
4. **No real Latin AZW3 exists in the repo**, so the Latin positive control is a synthetic paragraph
   injected into the real book's own document (same engine, same width) — stated as an AGENTS.md
   exception.
5. **RTL is not exercised** — the right-edge oracle is LTR by construction.
6. **MD has no real book** in `test-books/`.

Screenshots (gitignored, local to the run): `.reports/justify-shots/{txt-latin,txt-cjk,azw3-cjk,epub-latin,epub-cjk}.png`,
all 1080×1920, all reached via Library → tap. **Pixels and computed style agree everywhere both were
obtained** — `txt-latin` shows fully justified Latin prose, `txt-cjk` shows the right edge still

## New detail for bug #369, bisected not assumed

`Azw3ReaderActivityTest.tappingNext_turnsThePage_advancesPosition` fails identically at this lane's
**own parent commit** with the justify rule absent — **and the single method passes in isolation in
both states.** So the failure is **within-class state leakage from the two sibling tests, not a
broken tap zone**. That is exactly the discrimination bug #369's row records as still unknown.
