# Bug #367 — #129's EPUB line-spacing slider was inert

## Root cause

ReadiumCSS applies `--USER__lineHeight` (and `--USER__textAlign`) only under
`:root[style*=readium-advanced-on]`. That attribute is set **only** when
`publisherStyles = false`, and `toEpubPreferences()` never set it.

So the slider emitted a CSS variable **no rule consumed**. The preference was submitted, the
variable moved in the root style, and the rendering never changed.

## Why it survived a `VERIFIED` feature

Feature #129 shipped this control and every test asserting *"the preference was applied"* stayed
green — because the defect sits **downstream of everything Kotlin can observe**. Nothing in the
Kotlin layer is wrong; the value simply never reaches a rule.

This is the session's recurring shape: a check that is correct in itself, placed where the failure
does not pass through.

## The measurement

Computed `line-height` in the live DOM, driven through the **production**
`store → observeDisplaySettings → toEpubPreferences` path on the real `en` EPUB:

| State | Computed `line-height` |
|---|---|
| **Before** — slider 1.5 | 24.2109px |
| **Before** — slider 2.0 (`--USER__lineHeight` demonstrably moved 1.5 → 2.0 in the root style) | **24.2109px — unchanged** |
| **After** — slider 1.5 | **24px** |
| **After** — slider 2.0 | **32px** |

Font size 16px unmoved throughout, so the change is the line box and not a scale shift.

Also confirmed on the **CJK** EPUB: `line-height` moves 24 → 32px there too. So #367 is fixed for
CJK books even though *justification* is not reachable for them (that is feature #174 / GH #2090,
a different gate: `cjk-horizontal/ReadiumCSS-after.css` carries no `USER__textAlign` rule).

## Verified in both layouts and at both submission points

- **Scroll** and **paged** (`readium-paged-on` live).
- At **open** (production `initialPrefs`) and on **live re-submission** through the Display sheet.

## Mutation evidence

Mutation (c) — hardcode `lineHeight` to 1.5 — turns the #367 test **RED** while E1 (justification)
stays **GREEN**. Mutation (b) — set `publisherStyles = false` but drop `textAlign` — leaves the #367
test **GREEN** while E1 goes RED.

That separation matters: it proves the suite distinguishes the two properties rather than passing or
failing as a block, and that **the flag alone is what fixes line-height**.

## Fix

`android/app/src/main/kotlin/com/vreader/app/reader/EpubPreferencesMapper.kt` now submits
`publisherStyles = false` alongside `textAlign = JUSTIFY`. The two are **inseparable** — `textAlign`
is inert without the flag — which is why #156 WI-2 fixes this bug as a consequence of doing its own
job, and why splitting them would have shipped one change that is a no-op and another that makes it
work.

## Blast radius

`publisherStyles = false` switches every EPUB from publisher styling to ReadiumCSS user styling.
That radius is enumerated and each item verified by computed style — see the #156 row and plan §7.2,
including **two effects the plan's own enumeration missed** (E1b: publisher `text-align` on `p`/`li`
overridden and `text-align-last` forced to `auto`; E1c: the rule targets `:root`, so headings inherit
justification).

Independently confirmed and pinned: `publisherStyles = false` does **not** change which stylesheets
Readium injects.
