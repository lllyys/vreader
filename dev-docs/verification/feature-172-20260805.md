## Observations

**The fix is confirmed by the test that caught the problem, not by a new one.** `TxtTocAcceptanceTest`
is byte-identical to the version that failed at 8,300–11,449 ms; only the engine changed. That is the
strongest available evidence, and it is why WI-3 was specified as a re-measurement rather than a new
suite.

**Open-to-first-page moved 47→71 ms quiet.** Both are far inside the 2,000 ms target and the
concurrent arm actually improved (7→5 ms), so this reads as run-to-run variance on a loaded emulator
rather than a regression — but it is recorded rather than smoothed over, because the criterion is
"compared against the pre-change figures so a regression is visible rather than merely absent".

**The memory anomaly closed with the latency, as §4.5 branch 1 predicted.** The PSS signal during the
quiet scan is +12 MB where it was ~1.05 GB, and the earlier lowmemorykiller truncations have not
recurred across the runs since WI-2. Per the WI-1 audit this remains stated as **association**: the
growth travelled with the shipped path and disappeared with the rewrite. No separate bug row was
needed.

**WI-4 and WI-5 are not triggered and should not be built.** WI-1's arm (d) measured line-start
enumeration's *floor* at 75–89 ms — worse than the 61 ms the layer-1 fix achieves — so layer 2 cannot
beat layer 1 on this corpus. Room persistence (F1) is likewise unnecessary: the first open of the
largest real book in the corpus now costs 74 ms.

**What is brittle for next time.** Fixtures are wiped by every connected run, so a forgotten push
produces five loud failures rather than a silent skip (verified — that is the `requireNotNull` guard
working). Measurements exist only in logcat and must be collected retrospectively.
