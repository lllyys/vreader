## Observations

- **AZW3 live-render is `documented-injecting`, the sanctioned #68-class limitation — and it is honest, not a hand-wave.** The AZW3 theme background lands *inside* the foliate WebView (`body { background-color: … !important; }`) with **no Compose backdrop** (unlike PDF, which paints the theme on the Compose viewer backdrop and IS screencap-readable). The hardware-accelerated WebView / `blob:` subframe surface is not read back by `adb screencap` — every capture of the foliate body was byte-identical blank white across load/page-turn, while logcat + gfxinfo + the two passing render connected-tests all prove the content genuinely renders. So there is no screencap-observable surface that changes with the AZW3 theme. The injection itself is proven: the WI-6 `Azw3DisplayCss` Dark blob (`#1a1815`) flows through `Azw3Document.setStyles → FoliateBridge.setStyles → eval(foliateSetStylesJs(css))` — the exact seam the 18 passing `Azw3DisplayCssTest` JVM tests pin — and re-injects on every settings change (`Azw3ReaderActivity` `LaunchedEffect(holder, displaySettings)`). The theme/font/margin rules ride the same single `readerAPI.setStyles(css)` call, so if any renders (and the reader demonstrably renders), all do. This mirrors exactly how iOS #68 shipped AZW3 (documented-injecting; the drop-cap rule rides the same `setStyles` batch as the font/color rules that visibly render).
- The WI-4 Gate-4 audit caught and fixed a real settings-store write-ordering race (rotation double-consumer + silent consumer death) — now a process-wide Mutex + synchronous per-field submission-sequence latest-wins. The WI-7 Gate-4 caught a dark-theme "bright flash" — composition is now gated on the first settings emission. Both are exercised by the connected tests here.
- Persistence is DataStore-backed and device-local (`noBackupFilesDir`), so it survives process death; the cross-activity read at reader-open is the meaningful end-to-end persistence proof.
