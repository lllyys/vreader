# Feature #138 — Android paged phase-1: windowed / incremental pagination for very large docs

Gate-5b final acceptance for feature #138, the windowed-pagination follow-up filed from #137 WI-11.
All 9 WIs merged (`android/v0.20.7` → `android/v0.20.14`, merge commit `899321ee`); this evidence
flips the row `DONE` → `VERIFIED`.

Feature #137's Compose paged renderer measured the whole document once (phase-1 `TxtPaginator.index()`)
before showing the first page — **~96 s median** on the real 14 MB CJK book (#137 WI-11 evidence).
#138 replaces that blocking open with a **windowed / incremental** phase-1: `PaginationSession`
(single-Mutex owner) seals only an initial window, publishes it, and completes the full page-start
index in a coalesced background loop — with on-demand forward extension for jumps into unmeasured
regions. Result: **open-to-first-page is bounded regardless of document size** (measured **8 ms**),
while the full index remains byte-for-byte identical to #137's whole-doc `index()`. Paged stays
opt-in (default = Scroll, unaffected).

## Observations

- **Open-to-first-page collapsed from ~96 s to 8 ms** — a ~12,000× improvement, STRUCTURALLY
  independent of book size (only the initial 3-page window is sealed before the first publish;
  `firstWindowPages < pageCount` asserts the first publish is genuinely partial). This is the entire
  thesis of #138 and it is met with enormous margin.
- **The full index is byte-for-byte identical to #137's `index()`.** Windowing changed only WHERE the
  measure pass pauses/publishes, never the resulting page boundaries — proven by `assertArrayEquals`
  against a same-run non-windowed `index()` (30,695 identical page-starts). Memory posture unchanged
  (peak PSS 290 MB ≈ #137's 296 MB) since only the page-start IntArray is retained.
- **Far-jump into an unmeasured region resolves exactly with no UX regression.** A jump to ~90%
  (frontier at jump = 616, far behind the target) sealed on-demand THROUGH the target and landed on
  the exact page — asserted against a non-windowed ground-truth index. The recorded extend_ms=13496
  is the honest coalesced (background + on-demand) latency the plan asks to RECORD, not gate.
- **Two audits, complementary defect classes (the "deep AND broad" reconciliation).** A 5-lens
  adversarial workflow returned ship-as-is; the broad Gate-4 Codex pass (gpt-5.5/high) round 1 caught
  three real false-green risks the per-claim fan-out missed — a **synthetic-fallback that made the
  acceptance hollow**, **stated targets that were logged but only asserted at looser ceilings**, and a
  **far-jump exactness check that short-circuited when the index was complete**. All fixed (require the
  real book; assert the < 2 s / ≤ 300 MB TARGETS; unconditional far-jump range + non-windowed
  ground-truth parity) → Codex round 2 ship-as-is. Evidence:
  `.claude/codex-audits/feat-138-wi6-perf-acceptance-audit.md`.
- **Connected lifecycle re-push discipline (recurring Android lesson):** the connected task uninstalls
  the app at run-end and wipes `/sdcard/Android/data/com.vreader.app/`, so the real book must be
  re-pushed before each run. The acceptance methods `requireNotNull(readRealBookOrNull())` — a bare
  re-run without the pushed book fails loudly rather than false-greening on synthetic.
