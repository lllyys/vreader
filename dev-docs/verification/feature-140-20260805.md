# Feature #140 — Android AZW3 Contents (TOC)

Gate-5b acceptance pass. All eight implementation WIs merged (`android/v0.22.1` → `v0.23.2`).

## The user-visible path (rule 47 Gate 5 — production reachability)

> **app launch → `MainActivity` (the manifest LAUNCHER) → Library grid → tap the
> "Bei Tao Yan De Yong Qi - Zi Wo" tile → `Azw3ReaderActivity` → bottom-chrome "Contents" →
> tap chapter row 35 「要不要活在别人的期待中？」 → the reader navigates there and that row becomes
> the highlighted one.**

No `Azw3ReaderActivity.intent()` shortcut, no `src/debug` launcher, no composable invoked
directly. The opened reader is asserted to carry the book's fingerprint in the production intent
extra.

**Two bounds, stated rather than glossed:**

1. `ActivityScenario.launch(MainActivity::class.java)` starts the launcher activity **class**. That
   `MainActivity` is the LAUNCHER and `Azw3ReaderActivity` is non-exported are **static
   `AndroidManifest.xml` facts**, not dynamically exercised launcher-filter dispatch. Same posture
   as `feature-139-20260805.md`.
2. **No instrumentable release variant exists** (no `buildTypes` block; release is unsigned), so
   this ran on **debug**, which shares `src/main` with release.

## Criterion 7 is PARTIAL, and this is the honest statement of it

`test-books/books/azw3/` holds **exactly one** real AZW3 and **it has a TOC**. There is no real
no-TOC fixture, so **no real no-TOC book was opened.**

What *is* asserted here is the half that makes the check non-vacuous: after `Loaded`, the chrome
genuinely rendered (`chrome-notes` present), so a "Contents is hidden" assertion would have **teeth**
rather than passing on a blank screen. That distinction is the #139 lesson — a stuck pipeline must
not satisfy a hidden-control check.

The hidden-control behaviour itself is covered by
`Azw3ReaderChromeUiTest.emptyToc_hidesContents_notesStillPresent` (real chrome stack, empty entries →
no `chrome-contents`, Notes still present), re-run **14/0** in this pass, and structurally by
`ReaderChromeScaffold`'s `tocEntries.isEmpty()` rule.

## Depth coverage — stated precisely, not rounded up

The fixture's TOC is **hierarchical but shallow**: 15 root nodes → **71 rows**, depth histogram
`{0: 15, 1: 56}`, **maxDepth 1**.

So **real-book nested coverage is evidenced at depth 1 only.** Depth ≥ 2 rests on the JVM suites
(`FoliateTocParserTest` / `FoliateTocProviderTest` over synthetic deep trees) plus #139's on-screen
depth-3 indentation verification of the same rows, sheet and depth field. **This is not full
hierarchical coverage and must not be read as such.**

## The ack lies — observed, not argued

`Azw3TocConnectedTest.realBook_goToBogusHref_doesNOTChangePosition` recorded the bogus jump acking
**`Succeeded(cfi=null, fraction=null)`** while the position did **not** move.

That is the `Azw3GoToSliceTest.kt:90` trap (`Succeeded || Timeout`) demonstrated in the live system.
It is why every navigation assertion in this feature is a **position change** and never a result
value, and why WI-3 deliberately introduced no assertion of that shape.

## What Gate 4 caught that the tests would not have

Three rounds; R1 2 High + 3 Medium + 2 Low, R2 1 High + 1 Medium + 1 Low (`block-recommended`),
R3 clean → `ship-as-is`. Both Highs were real and load-bearing:

- **Criteria 4 and 5 were asserted in two independent waits**, so drift could have satisfied them
  separately. Fixed with **one href-bound window**: the highlighted row index comes from
  `foliateTocIndexFor` over `relocate.tocHref`, so only a report naming the tapped href can produce
  it — and the position is read while that highlight still holds.
- **The title checks were circular**, validated against the same provider run that produced them.
  Fixed with `EXPECTED_TOC_DIGEST`, a SHA-256 over all 71 rows' `(depth, title, href)`.

**Two of the lane's own fixes were disproved by the device rather than by review**: `CollectionInfo.rowCount`
publishes `-1` for this `LazyColumn`, and scrolling to the last index left row 0 off-screen. Both
surfaced only because the gate was re-run after each audit-driven change.

## Known pre-existing failure, not this feature's

`Azw3ReaderActivityTest.tappingNext_turnsThePage_advancesPosition` fails on `azw3-next-zone is not
displayed` — **bug #369 / GH #2080**, bisected to WI-5 HEAD. This suite deliberately observes the
same tap zones by **existence** rather than `assertIsDisplayed`, so it does not inherit that failure
mode.

## Scope not claimed

The hostile-payload tests prove the **payload** parses. They do **not** claim a pathological *book*
opens — foliate's own `assignIDs`/`flatten`/`serializeTOC` recurse inside `readerAPI.open()` before
Kotlin sees anything. That exposure is pre-existing and unchanged by #140 (plan §5.4 CLAIM /
NOT CLAIMED, risk R13, follow-up F6).
