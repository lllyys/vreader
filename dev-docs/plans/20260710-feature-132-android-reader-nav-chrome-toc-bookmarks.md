## Structure decision

**Recommendation: SPLIT bookmarks into a sibling feature #135** (kept from v3; round-2's decision, unchanged). The round-2 audit showed the bookmark machinery carries most of the feature's complexity — five hard, coupled sub-problems — and #132 does NOT need any of it to complete its own parity boxes. The split lets #132 (chrome shell + TOC + annotations-review sheet + backup) land clean while #135 owns the bookmark hard problems as a coherent unit.

**What is a bookmark problem vs a #132 problem:**

| Hard problem (round-2) | Owner | Why |
|---|---|---|
| (a) canonical→Readium locator **reconstruction** (`toReadium`) | **#135** | only needed to JUMP to a persisted bookmark; TOC jump uses the *retained native* Readium locator (no reconstruction) |
| (b) awaited AZW3 `goTo` bridge | **#135** | only needed to jump to a bookmark on AZW3; #132's AZW3 host ships `EmptyTocProvider` + chrome, no in-session goTo |
| (c) unique-index Room migration + dedupe | **#135** | the uniqueness constraint exists to make bookmark *creation* idempotent; #132 never creates a bookmark |
| (d) toggle/state across all hosts (top-bar Bookmark toggle + `bookmarkForLocator`) | **#135** | the only designed bookmark *creation* affordance is the top-bar toggle |
| (e) bookmark backup *population* (the create path filling the list) | **#135** | bookmarks only become creatable there; the envelope + collect/restore of the list is wired in #132 (see the backup-ownership resolution) |

**What #132 keeps (and why it's still coherent without bookmarks):**
1. **Chrome shell** (top bar + bottom-chrome Contents/Notes slots un-omitted) — but the **top-bar Bookmark toggle renders in a DISABLED/omitted state until #135** (see §top-bar-bookmark-omission), so #132 does NOT ship a dead bookmark control (the #129 Gate-2 dead-control rule). The top bar's Library/title are live; Search/More stay omitted until #133/#134.
2. **TOC / Contents** — the Contents tab of `TOCSheet` (chapter rows → jump), using the *retained native* Readium locator. **The Bookmarks tab is NOT built in #132** (it has no data source and no create path until #135) — the `TOCSheet` ships Contents-only in #132; #135 adds the Bookmarks tab. This is design-faithful: `vreader-panels.jsx` `TOCSheet` has both tabs, but a tab with no populated/empty data path is exactly the dead-control anti-pattern — #135 lights the Bookmarks tab when it has bookmarks to show.
3. **Annotations-review sheet** (`AnnotationsSheet`, the box-B remainder) — highlights + standalone-notes review, filter chips, cards, sheet-level Share, and tap-to-jump. **The `Bookmarks` filter chip + `BookmarkCard` are #135** (no bookmark data until then). #132 ships the sheet with the `All / Highlights / Notes` chips; #135 adds the `Bookmarks` chip + card. The Notes bottom-chrome slot has a real destination in #132 (highlights + notes review) → NOT a dead control.
4. **Annotation backup/restore** — extend `BackupCollector`/`RestoreImporter` to emit + restore the contract's `annotations.json` **highlights + notes + bookmarks** (verified `BackupAnnotationsEnvelope` has all three lists). #132 owns the FULL envelope collect+restore; bookmarks are collected too (the read exists: `bookmarksForBook`) so the list is present and fully wired — it is simply empty when the DB has no bookmarks, not "present-but-empty by design." See the backup-ownership resolution below.

**Backup ownership — RESOLVED (round-3 MEDIUM fix, the WI-8 version is authoritative):** the opening/table above previously read "bookmark backup → #135," which contradicted WI-8's correct design that #132 collects + restores ALL THREE `BackupAnnotationsEnvelope` lists. The authoritative statement: **#132 owns the FULL `annotations.json` collect + restore round-trip (highlights + notes + bookmarks).** The `bookmarks` list is present and **FULLY WIRED** in #132 — the collector queries all bookmarks and the importer restores them by preserved UUID. It is empty only when the DB has no bookmarks. Because `addBookmark`/`bookmarksForBook` already exist (verified `AnnotationsRepository`/`AnnotationDao`), bookmarks **may be non-empty even pre-#135** if any code path created one. Consequently **#135 needs NO `BackupCollector`/`RestoreImporter` change** — only the bookmark creation/toggle/list/jump surface plus its integration-time unique-index migration. The table row (e) above therefore names only "bookmark backup *population*" (the create path) as #135's — the envelope wiring itself is single-writer in #132.

**Why the Notes slot is NOT dead in #132 without bookmarks (the v2 CRITICAL, re-answered):** v2's argument was "un-omitting Notes with no destination is a dead control." True — but the destination is the **annotations-review sheet showing highlights + notes**, which #132 fully builds. Bookmarks are one of three annotation kinds in that sheet; the sheet is a live, useful destination with just highlights + notes (a reader with highlights but no bookmarks is the common case). So the Notes slot lights up correctly in #132; #135 only *adds* a chip + card kind to an already-live sheet.

**Why split now (the cohesion counter-argument, re-answered):** v2 kept them together for "one user story." But the round-2 findings prove the bookmark sub-story is a large, independently-testable unit (locator reconstruction + awaited AZW3 bridge + migration + cross-host toggle + create-path backup) whose acceptance is orthogonal to "I can review my highlights and browse chapters." Splitting draws the line at the natural seam: **#132 = read/review/navigate; #135 = mark.** Each is a coherent user story. Rule 47's audit-count table favors this: #132 becomes ~10 WIs (Large but bounded), #135 ~7 WIs, versus one ~14-WI feature whose highest-risk WIs (AZW3 awaited goTo, EPUB `toReadium`) all serve the bookmark story.

**Cost of the split:** two features, two merge cadences. The `annotations.json` envelope is **single-writer in #132** (highlights + notes + bookmarks list all wired here); #135 only fills the bookmarks list via its create path, touching no collector/importer code. This removes the "two writers on the backup contract" cost the split might otherwise imply.

**Rejected — keep everything in #132 (v2's choice (a)).** Rejected because the bookmark hard problems (a)–(e) are the round-2 CRITICAL/HIGH surface and none of them is needed for #132's own parity completion; folding them in makes #132's highest-risk WIs serve a sub-story that can ship independently, and inflates one feature past the comfortable audit-count band.

## 1. Problem

The Android readers ship only minimal chrome: EPUB (`ReaderActivity`) has a View-based back-button + title bar (verified: `buildChrome()` builds a `LinearLayout` bar + `FrameLayout` navigator host + a `ComposeView` `PopoverOverlay` that collects `popoverVm.state` via `collectAsStateWithLifecycle`); TXT/MD (`TxtReaderActivity`), PDF (`PdfReaderActivity`), AZW3 (`Azw3ReaderActivity`) each have a bespoke Compose `*Scaffold` (back chevron + serif title). Feature #129 built the designed `ReaderBottomChrome` (scrubber + a single **Display** slot) with Contents/Notes/AI slots omitted "until F/D". There is no top bar (Library/title/search/bookmark/More), no TOC panel, and no annotations review list — even though the highlights/notes persistence layer already exists (#123–#125) and is unreviewed in-app.

**Verified persistence + navigation facts:**
- **Annotations persistence exists (no review UI):** `AnnotationDao` (`data/Daos.kt`) has `observeHighlights`/`highlightsForBook`/`allHighlights`, `observeNotes`/`notesForBook`, `observeBookmarks`/`bookmarksForBook`; the repo seam `AnnotationsRepository` exposes `highlights(bookKey)`, `notes(bookKey)`, `bookmarks(bookKey)` Flows + `addHighlight`/`addNote`/`addBookmark`/`removeHighlight`/`removeNote`/`removeBookmark`/`updateHighlight`/`findHighlight`. **There is NO all-notes and NO all-bookmarks snapshot read** on the DAO (only per-book `notesForBook`/`bookmarksForBook` + `allHighlights`) — WI-8's collector adds them. **There is NO standalone-note UPDATE API** (only `updateHighlight(id,color,note)` for highlight-attached notes) — a HIGH gap for the review sheet's note-Edit (§review-sheet-contract). **Critically, the create methods MINT NEW UUIDs** (`addHighlight`/`addNote`/`addBookmark` all call `newAnnotationId()`, verified) — so a restore that must PRESERVE backed-up UUIDs cannot reuse them; the restore seam is a NEW transactional path (§annotation-restore-seam). The `AnnotationsSheet`/`HighlightsSheet` is a **design only** (`vreader-android-annotations.jsx`), not code.
- **`BackupCollector` backs up NEITHER annotations NOR bookmarks** (verified: it emits `positions.json`, optional `collections.json`, and the library manifest — nothing else). `RestoreImporter` restores books + positions + collections only (verified). Restore drops all highlights/notes/bookmarks today — a **silent data-loss gap** the moment any annotation-review or bookmark UI ships.
- **The backup contract ALREADY mandates ONE `annotations.json`:** `vreader.contracts.backup.BackupAnnotationsEnvelope` (verified `android/identity/.../backup/BackupSections.kt`) is `{ schemaVersion, highlights: List<BackupHighlight>, bookmarks: List<BackupBookmark>, notes: List<BackupNote> }`, field-identical to the Swift `BackupSectionDTOs.swift`. `BackupHighlight`/`BackupBookmark`/`BackupNote` each carry `bookFingerprintKey` + `locatorJSON` (a **plain canonical `Locator` JSON**, per the `HighlightEntity` comment: the collector MUST emit `record.locator.canonicalJson()`, NOT the stored round-trip column) + timestamps + the record UUID. **`bookmarks.json` is NOT a contract alternative — no contract extension is needed; the section is `annotations.json`.**
- `Locator` (`android/identity/.../contracts/Locator.kt`, verified) is `{ contentSHA256, fileByteCount, format, href?, progression?, totalProgression?, page?, charOffsetUTF16?, charRange…?, cfi?, textQuote?, textContext…? }`; `fingerprintKey` is derived; `canonicalJson()` is the equality basis. A locator cannot be built from a Readium/foliate position alone — the `Book` identity triple must be threaded in.
- **`ReadiumLocatorBridge` is ONE-directional** (verified — the CRITICAL): it converts a Readium **Locator JSON string** → `VReaderLocator` envelope + a canonical fallback `Locator` (`toEnvelope`), and returns the verbatim Readium JSON back out (`readiumLocatorJSON`). It has **NO Readium dependency** (pure-JVM, consumes JSON) and **NO `toReadium`/`toCanonical(readiumLocator, book)`**. Critically, it does NOT go canonical `Locator` → a valid Readium `Locator` object — and `org.readium.r2.shared.publication.Locator.fromJSON(canonicalJson)` is **not** valid (the canonical `Locator` JSON is vreader's shape, not Readium's). This is the bookmark-jump reconstruction problem — **owned by #135** (§135-locator-reconstruction).
- **Readium navigation API (verified via existing `ReaderActivity` usage):** `nav.currentLocator.value` yields an `org.readium.r2.shared.publication.Locator`; `locator.href` is an `Href` (used as `.href?.toString()` in `currentHref()`); `navigator.go(locator)` is the jump seam. `publication.tableOfContents` (property) + `publication.locatorFromLink(link)` are the TOC-flatten inputs (grounded against the Readium 3.3.0 API surface the app already links; `readingOrder`/`Publication` are imported and used in `BookOpener`). `Link.children`/`Link.title` are nullable.
- **AZW3/foliate `goTo` is fire-and-forget with no result** (verified — the CRITICAL): `FoliateBridge` exposes only `init()/initAtCfi()/initAtFraction()/next()/prev()`, each a `webView.evaluateJavascript(js, null)` wrapped in `try{…}catch(e){}` that **swallows nav errors and discards the callback**. The bundle's `readerAPI.goTo(target)`/`goToFraction(f)` DO exist but call `view.goTo(...)` **without returning the promise** — so an error or a no-op is invisible. `Azw3Document.restoreOrInit()` applies CFI/fraction **only at book-ready**; there is no in-session goTo and no pending-goTo re-issue after `onRenderProcessGone`. The bundle DOES dispatch a `relocate` event (`FoliateMessage.Relocate{cfi,fraction,sectionIndex,sectionTotal}` is parsed) — this is the acknowledgment channel an awaited goTo can key on. **The awaited AZW3 goTo bridge is owned by #135** (§135-azw3-goto).
- **DB is v5** (verified `@Database(version = 5)`, entities include `BookmarkEntity`); `ALL_MIGRATIONS = [MIGRATION_1_2 … MIGRATION_4_5]`; `exportSchema = true`. The highlights table already has the precedent #135 reuses: a unique `Index(["profileKey","anchorKey"])` + a transactional insert-if-absent-then-update (`AnnotationDao.upsertHighlight`, verified). `BookmarkEntity` has `Index("bookKey")` only — **no uniqueness on position** (the #135 toggle-atomicity target). **#132 adds NO migration.**

### §annotation-restore-seam — UUID-preserving transactional restore (round-3 HIGH fix)
WI-8's acceptance says "re-insert by UUID," but **no restore API exists and every create method mints a NEW UUID** (`addHighlight`/`addNote`/`addBookmark` → `newAnnotationId()`, verified). Reusing them would fabricate ids and defeat idempotency. So #132 pins a dedicated restore seam:
- **API:** `AnnotationsRepository.restoreAnnotations(env: BackupAnnotationsEnvelope, allowedBookKeys: Set<String>): RestoreAnnotationsReport`, backed by an `@Transaction`-wrapped `AnnotationDao` restore method. It **preserves the backed-up `id` and `createdAt`/`updatedAt`** verbatim (maps `BackupHighlight`/`BackupNote`/`BackupBookmark` → the entity with the backup's UUID, NOT a freshly-minted one).
- **Per-kind merge rules (explicit):**
  - **highlight:** insert-if-absent by `highlightId` (UUID) first; on a UUID collision skip (idempotent). The existing profile-key/`anchorKey` unique index still guards against a *different-UUID same-anchor* duplicate — so the merge is **UUID first, then the (profileKey, anchorKey) profile-key fallback** already enforced by `upsertHighlight`'s unique index (a same-anchor different-UUID row updates in place, not duplicates).
  - **bookmark:** insert-if-absent by `bookmarkId` (UUID) first; **profile-key/position fallback** applies once #135 adds the `(bookKey, profileKey)` unique index — until then the bookmark restore dedupes on UUID only (the pre-#135 state), which is correct because #132 never *creates* bookmarks so the only source of a bookmark is a prior backup with a stable UUID.
  - **standalone note:** insert-if-absent by `noteId` (UUID) **only** — a note has no profile-key/anchor uniqueness, so UUID is the sole dedupe key.
- **Validation:** each row's `Locator` must parse and its `fingerprintKey` must equal the row's `bookFingerprintKey` (the `requireSameBook` invariant) — a mismatched/corrupt locator row is **skipped, counted as a failure**, never inserted (poisoning the persistence boundary is worse than dropping one row).
- **Scope restriction:** only rows whose `bookFingerprintKey ∈ allowedBookKeys` (the successfully-restored / selected manifest books) are applied; a row for a book that wasn't restored is **dropped, counted as skipped** (matches iOS "annotations for a skipped book are dropped").
- **Report:** `RestoreAnnotationsReport(highlights: KindCounts, notes: KindCounts, bookmarks: KindCounts)` where `KindCounts(applied, skipped, failed)` — surfaced to the restore result UI as a per-kind count (the collector/importer already report per-section counts; this extends that).
- **Idempotency:** because every insert is insert-if-absent keyed on the preserved UUID, a repeated restore of the same backup produces zero new rows (`applied` drops to 0 on the second pass) — the tested invariant.

## 6. Risks + mitigations

1. **EPUB host is Fragment + View chrome + async-assigned publication (WI-7-EPUB, highest, now a DEDICATED WI).** Use the verified `PopoverOverlay` `ComposeView`+`collectAsStateWithLifecycle` precedent, a `MutableStateFlow<ReaderChromeModel>` fed as the open completes, **separately-sized top/bottom `ComposeView`s** (never one full-screen overlay over the reading area — it would eat Readium scroll/selection/link input) + a full-screen dismiss overlay ONLY while a sheet is open. The persistent StateFlow, touch-through sizing, TOC load, native-locator jump, and failed-jump behavior are all owned by WI-7-EPUB (round-3 HIGH fix — previously unowned). Do NOT rewrite the navigator. Isolate last.
2. **AZW3 has no bridged TOC (and #132 adds no goTo).** `FoliateBridge` exposes only `init*`/`next`/`prev` (verified); `FoliateMessage` maps outline/toc to `Other` (ignored). #132 ships `EmptyTocProvider` for AZW3 + chrome only, and its review-card tap-to-jump is `null` (capability-gated). The awaited `goTo` seam (CFI→fraction fallback, render-death re-issue keyed on the `relocate` ack) is **#135's** work (it's only needed to jump to a bookmark). #132 leaves `FoliateBridge`/`Azw3Document` untouched → zero AZW3-nav risk in #132.
3. **Contents slot on no-TOC hosts = dead control.** Hide when the provider yields empty; the Contents sheet is Contents-only and only reachable from a TOC host. Notes (review sheet) is reachable everywhere.
4. **Annotation backup was absent + restore mints new UUIDs.** Verified: `BackupCollector` emits only books/positions/collections; `RestoreImporter` restores only those; `BackupAnnotationsEnvelope` ALREADY exists (no contract change); the create methods mint new UUIDs so a naive restore fabricates ids. WI-8 adds the `annotations.json` round-trip through the §annotation-restore-seam (UUID-preserving, idempotent, per-kind report) + a live WebDAV round-trip. Canonical `locatorJSON` (not the stored round-trip column) is the one subtle correctness point (tested).
5. **Write-set overlap with #129 + #131 on `ReaderBottomChrome.kt` + `TxtReaderActivity.kt` (integration serialization, NOT a feature dependency — §write-set-serialization).** WI-5 (chrome file) + WI-6 (TXT host) land at integration after whichever of #129/#131 they collide with has merged; nullable-default params keep #129's `Display` + #131's `onOpenBilingual` callers valid; **re-audit WI-5/WI-6 after rebasing onto that baseline** — do not implement against an in-flight signature.
