## 1. Problem

The Android library has no search at all — no entry affordance, no search surface, and two data-layer gaps make the committed design unimplementable today:

- **No author field.** `BookEntity` (`android/app/src/main/kotlin/com/vreader/app/data/Entities.kt`) and the `Book` DTO (`data/LibraryRepository.kt` line 19) carry only `title`. iOS `Book` has `author: String?` (`vreader/Models/Book.swift`), and the shared backup contract already has an optional `BackupLibraryEntry.author` (`android/identity/src/main/kotlin/vreader/contracts/backup/BackupSections.kt` line 109) that Android hard-codes to `null` (`backup/BackupCollector.kt` line 139, comment: "Android `Book` carries neither") and never restores. The design's search field placeholder is literally "Search title, author, or text…" — author search cannot be built without the column.
- **No text index of any kind.** The design's results state shows an in-text snippet ("…the **pragmatic** programmer is quick to adapt…" — Ch. 1) and its no-results copy promises "Search looks across titles, authors, and the text of downloaded books." Android has no cross-book (or even per-book) text search; iOS has per-book FTS5 (`vreader/Services/Search/*`) but even iOS's *library* search is metadata-only.

### The author-clobber hazard (why `BookImporter` and restore CANNOT stay out of scope) — Gate-2 CRITICAL

Once `Book.author` defaults to `null`, the existing whole-row upsert becomes a **destructive** operation for the new column:

- `BookDao.upsert` is `@Upsert` (verified `data/Daos.kt` lines 22-23) — an insert-or-**UPDATE of the whole entity**. `BookImporter.importStream` builds a fresh `Book(...)` (verified `data/BookImporter.kt` lines 92-101, no `author` argument) with no author and calls `repository.upsertBook(book)` (line 103). A **duplicate SAF import of an already-indexed book** therefore UPDATES the existing row with `author = null`, silently erasing an author the coordinator (or a prior restore) had already backfilled.
- **Restore double-writes the row and both writes null the author.** `RestoreImporter.restoreBook` (verified `backup/RestoreImporter.kt` lines 129-152) calls `bookImporter.importStream(...)` (write #1: author null) and then a SECOND whole-row `repository.upsertBook(imported.copy(title = entry.title ?: imported.title, addedAt = entry.addedAt.toEpochMilli(), lastOpenedAt = entry.lastOpenedAt?.toEpochMilli()))` (write #2, lines 145-151) that does **not** carry `entry.author`. So even a manifest that has an author restores it as null today.
- **The bug is self-latching.** The coordinator's backfill only runs for books whose `search_index_state` row is missing/stale (see WI-5). A book that is already indexed but then re-imported (nulling its author) keeps a **current** index-state row, so the coordinator never revisits it and the null author is permanent.

**Resolution (applied throughout WI-1/WI-2/WI-5):**
1. Re-import must **preserve** derived metadata. `BookImporter` gets an author-preserving upsert seam: instead of blindly overwriting the whole row, the importer performs an **atomic partial upsert** — insert the new row if absent, else update only the import-owned columns (`title`, `originalFormat`, `contentSHA256`, `fileByteCount`, `localFilePath`, `sourceUri`, `addedAt`) and **leave `author` (and `lastOpenedAt`) untouched**. Author is derived data the importer never owns.
2. Restore applies its metadata through **ONE atomic DAO update** (see below) whose `SET` includes `title`, `addedAt`, `lastOpenedAt` AND `author = COALESCE(:manifestAuthor, author)` — a non-null manifest author overwrites; a null manifest author preserves whatever the coordinator already backfilled. The old second whole-row `upsertBook(...)` is **deleted entirely**.
3. The coordinator's own author backfill stays `UPDATE … WHERE author IS NULL` (write-only-if-null), so it never clobbers a restore- or import-preserved author.

The atomic partial-update DAO ops (`BookDao.insertIfAbsent` + `updateImportedColumns` + a transactional `upsertPreservingAuthor` for import, and the single restore-side `applyRestoredMetadata` update) land in WI-1 (foundational, but behavioral because they change persistence semantics) so every later WI builds on the safe seam.

### Design inventory (rule 51 — everything the plan builds, and only this)

**Depicted in `vreader-library-android.jsx` (the authoritative Android surface, section "C. Search"):**

1. **Entry**: a Search pill in the Library top bar (`LibraryScreen` trailing icons: Search + More). The shipped `library/LibraryScreen.kt` nav row already documents this slot. #128 adds the Search pill only (More/settings is another feature).
2. **Search screen** (full-screen takeover, status strip retained): rounded search field with search icon, placeholder "Search title, author, or text…", accent inset ring when active, trailing clear-X when non-empty, and a "Cancel" text button that returns to the Library.
3. **Empty state** (`state='empty'`): "RECENT" section label + recent-query rows (timer icon, query text, insert-arrow glyph) with hairline separators; "BROWSE COLLECTIONS" section label + collection chips (the user's collections, excluding "All").
4. **Results state** (`state='results'`): summary line "2 books · 1 in-text match"; result rows = small cover (62 w) + serif title with the matched substring wash-highlighted + author subtitle + (for books with a text hit) an italic serif snippet with the matched term wash-highlighted and a chapter attribution suffix ("— Ch. 1"), hairline row separators.
5. **No-results state** (`state='noresults'`): circled search icon, serif "No matches for "{q}"", sans copy "Search looks across titles, authors, and the text of downloaded books. Try a different term."
6. **Library grid author line**: `CoverGrid` shows an author subtitle under each title (currently degrades to nothing because the data is missing — lights up once `author` exists).

**The "No matches" copy is truthful ONLY when the whole indexable corpus is settled — Gate-2 HIGH (honest empty state).** The design's no-results copy asserts that search looked "across … the text of downloaded books" — a definitive claim. Showing it while indexing is still in flight (in-text hits not yet present) would be untruthful, and inventing a "still indexing / partial" state would self-design UI (rule 51). **Resolution chosen: option (a) — gate the definitive no-results copy on index completeness.** The no-results state renders the design's definitive copy ONLY when `search_index_state` covers every indexable book in a **settled** state; until the corpus is fully settled, a query with no metadata match and no (yet-available) text match renders **partial results without the definitive empty state** — i.e. metadata results are always shown live, and if there are zero metadata results while indexing is incomplete, the screen shows the results list (possibly empty of rows) but suppresses the "Search looks across … the text of downloaded books" definitive copy. Metadata-only (title/author) search is always complete, so a metadata "no match" is honest; the definitive text-inclusive copy waits for text-index completeness. No new visual state is introduced (the suppressed-copy branch reuses the existing empty results list); option (b) `needs-design` is NOT required for this autonomous path. `SearchViewModel` exposes an `indexComplete: Boolean` derived from a coordinator/`SearchDao` completeness check so the composable can gate the copy without inventing chrome.

**Completeness is defined over SETTLED states, not `indexed` alone (Gate-2 round-3 HIGH — `skipped_unsupported` must not block completeness forever).** A book whose format cannot yield text on Android (a protected/malformed EPUB with no content service) reaches a **terminal settled state** the coordinator can never improve on. If completeness required *every* indexable book to be `indexed`, a single no-content-service EPUB would leave `indexComplete = false` **permanently**, suppressing the definitive no-results copy forever. So completeness is: **every indexable book (format ∈ {epub,txt,md}) has a `search_index_state` row whose status is a SETTLED value — `indexed` OR `skipped_unsupported`** (both are terminal: an `indexed` book contributes its text, a `skipped_unsupported` book is honestly metadata-only and cannot ever contribute text). The only states that keep completeness `false` are the *non-settled* ones — a **missing** state row (not yet visited) or a **`failed`** row (a retryable transient error still eligible for reindex). `failed` is deliberately non-settled: it holds `indexComplete` open only while a genuine retry is pending, and the coordinator re-attempts it (next launch / on `indexerVersion` bump), so it converges to `indexed` or `skipped_unsupported` rather than latching. This makes `skipped_unsupported` a *counted, settled, metadata-only* result — not a perpetual gap — while still refusing to claim "we searched the text" before a genuinely-missing or still-retrying book is resolved.

**Depicted only in `vreader-search.jsx` (iOS reader-frame search sheet) → OUT of scope for #128:** the "This book / All books" scope toggle; operator-syntax chips (`"exact phrase"`, `darcy AND elizabeth`, `chapter:1`, `highlighted:yellow`, `note:`); the "FTS5 with CJK tokenization" helper copy; per-chapter grouped result lists with `p.N` page badges, per-group match counts, and chevron jump-to-location rows; "Tap to repeat" recents labels. These belong to an **in-book search** surface (an Android reader-chrome feature that doesn't exist yet) and to iOS.

**Not depicted anywhere → scoped out or needs-design:**
- Jump-to-hit inside the reader from a library search result (no locator resolution in #128; tapping a result row opens the book at its saved position, exactly like tapping it in the grid).
- Indexing-progress indicator — no such state is drawn; in-text results simply appear once indexing completes (metadata results are always live). Honest limitation handled by the completeness-gated no-results copy above (no invented state).
- Search operators/boolean syntax, per-book multiple snippets, search scoped to a collection, sort/filter controls, an empty state for "no recents and no collections" (render sections only when they have content — the `LibraryScreen.kt` collection-empty precedent, Gate-4 WI-3 Medium in #127).

### In-text format scope (honesty boundary)

| Format | Text source on Android | In #128? |
|---|---|---|
| EPUB | Readium 3.3.0 `Publication` content service — `Publication.content(locator)` extension (`org.readium.r2.shared.publication.services.content.ContentServiceKt.content`, verified present in the shipped readium-shared 3.3.0 jar) returning a `Content` whose suspend `iterator()` streams `Content.TextElement`s. `BookOpener` already opens publications. **`content()` is NULLABLE** — it returns `null` when the publication has no `ContentService` (verified: `content$default` bytecode returns `aconst_null` when `getContentService` is null) — handled as a typed unsupported result (see WI-3). | **Yes (when content service present)** |
| TXT | `reader/TxtDecoder` (BOM/UTF-8/GBK detection) + `TxtDocument` chunking — pure JVM, already shipped | **Yes** |
| MD | Same decode path as TXT (raw markdown text; marker-stripping is a nice-to-have) | **Yes** |
| PDF | `android.graphics.pdf.PdfRenderer` has **no text-extraction API** at minSdk 26 (page-text APIs are API 35+) | **No — metadata-only** |
| AZW3 | Text exists only inside the foliate-js WebView; no JVM-side MOBI/KF8 parser | **No — metadata-only** |

The design's copy ("the text of downloaded books") doesn't enumerate formats, so shipping in-text for EPUB/TXT/MD and metadata-only for PDF/AZW3 is honest; PDF/AZW3 books still match by title (and EPUB-derived author). Nothing in the UI claims PDF text is searched. An EPUB whose `content()` is null (no content service — protected / malformed) is treated as a metadata-only book and recorded as a typed **settled** skip (`skipped_unsupported`, see WI-5 failure/skip semantics) so it counts toward "corpus settled" without ever contributing text.

## 2. Surface area

### Architecture decision — ALL search tables live in the single `vreader.db` (Gate-2 round-2 CRITICAL)

The v2 plan proposed a *second* Room database file (`search-index.db`) purely to make an Auto-Backup exclusion file-scoped. **That split is REJECTED — it is architecturally incoherent:**

- **SQLite forbids cross-schema foreign keys.** `search_sections`, `search_index_state`, `search_sections_staging`, and `search_sections_fts` must FK/CASCADE to `books`. A FK from a table in `search-index.db` to `books` in `vreader.db` is impossible in SQLite (foreign keys cannot span attached databases / different schema files). Losing the CASCADE would leave orphaned index rows on every book delete and force manual cleanup.
- **A Room `@Transaction` spans exactly ONE database instance.** The coordinator's cancellation-safe atomic publish must write sections **and** the index-state row **and** backfill `books.author` in one commit (§Coordinator). If `books` lives in `vreader.db` and the search tables in `search-index.db`, no single `@Transaction` can span them — the atomicity HIGH cannot be satisfied.
- **The completeness join** (`search_index_state` vs the `books` corpus) is a plain SQL join inside one DB; splitting it forces a cross-DB read in Kotlin.

**Chosen architecture: one database.** All four search tables (`search_sections`, `search_sections_fts`, `search_index_state`, `search_sections_staging`) are added to the existing `VReaderDatabase` (`vreader.db`) at schema **v7**, with the FK→`books` CASCADE, the `@Transaction` atomic publish, and the completeness join all working natively.

### Auto Backup — the search index STAYS in the (default) Android Auto Backup (Gate-2 round-3 HIGH — dropped the incoherent `vreader.db` exclusion)

**No `dataExtractionRules` / `fullBackupContent` exclusion is added by this feature. The default Auto Backup config is kept as-is, and that default is the *coherent* choice — verified against how the app actually stores data.**

The v3 plan proposed excluding the whole `vreader.db` file from Android Auto Backup, justified by a claim that Auto Backup "never carried book blobs anyway." **That claim is factually WRONG, and the exclusion is INCOHERENT with the codebase** — it was the root of a 2-round flip-flop and is now removed entirely:

- **Books live under `filesDir/books` — which Android Auto Backup includes BY DEFAULT.** `AppContainer` constructs `BookImporter(File(appContext.filesDir, "books"), repository)` (verified `VReaderApp.kt` line 31); `BookImporter` copies each imported book's bytes into that `booksDir` and stores `localFilePath = finalFile.absolutePath` (verified `data/BookImporter.kt` lines 37/64/85/98). So the book **blobs** are in `filesDir`, and Auto Backup's default rule set includes all of `filesDir` except `noBackupFilesDir`. The blobs ARE backed up by default.
- **Excluding only `vreader.db` would restore book FILES without their METADATA.** If `filesDir/books` is (by default) backed up but `vreader.db` is excluded, an Auto-Backup restore recreates every book blob on disk with **no `books` row pointing at it** → the library shows **empty** while orphaned blobs consume storage. That is strictly worse than the default, and it is exactly the failure the v3 exclusion would have shipped.
- **No Android WebDAV recovery path is wired yet** (verified: `architecture.md` line 583 "No production user entry yet (the #114 UI is the seam; its production wiring is design-gated)"; **zero** matches for `WebDavBackupService` / `BackupService` / `WebDavClient` in `VReaderApp.kt` — `AppContainer` does NOT construct the backup service). So the v3 premise that "the WebDAV/manifest path is the app's real backup" is not yet true on Android: **Android Auto Backup IS the only restore mechanism a user has today.** Breaking metadata restore to save index size would remove the *only* working restore path.

**Chosen policy: keep `vreader.db` in the default Auto Backup (books + metadata restore together, coherently).** The FTS/search index and its staging table add **bounded** size to the (existing, default) Auto Backup. This is acceptable because:
- (a) With no Android WebDAV recovery wired, Auto Backup is the *only* restore today, and it only works if the DB (metadata) and `filesDir/books` (blobs) are backed up **together** — which the default already does.
- (b) The index is device-local **derived** data; if a future Auto-Backup restore carries a stale/partial index, the coordinator reconciles it on first launch (content-addressed identity means it re-extracts anything not settled). So even a backed-up index is self-healing, never a correctness hazard.

**Index size is a bounded, revisit-later concern, not a reason to break restore.** The corpus text roughly doubles the DB (the FTS content column + `indexedText`); the staging table is transient (cleared per book). If Auto-Backup quota (~25 MB) ever becomes a real problem, the ONLY safe future move is to exclude the index **only if/when Android WebDAV recovery ships** (so metadata restore has an alternative), AND note a hard constraint: **a table-level Auto-Backup exclusion is impossible** — Android backup rules operate on **files/folders, not tables**, so you cannot exclude "just the index tables" of `vreader.db`. Excluding index-only would require physically splitting the index into a *separate DB file* — which reintroduces the cross-schema-FK problem this plan already rejected (§Architecture decision). Hence: no exclusion now; if it's ever needed, it is a dedicated follow-up feature (its own design + a WebDAV-recovery precondition), not a line item here.

`RecentSearchesStore` (DataStore under `noBackupFilesDir`) is device-local by construction — `noBackupFilesDir` is never in the Auto-Backup set (the shipped `reader_settings.preferences_pb` precedent, `VReaderApp.kt` lines 58-62). That is unchanged and needs no rules file.

(No `search-index.db` file, no second `@Database`, no second DAO, no separate exported schema, **and no `res/xml/*` backup-rules files or manifest backup attributes** — all removed from this plan.)

### New files — data layer (`android/app/src/main/kotlin/com/vreader/app/data/`)

- **`SearchEntities.kt`** (the `CollectionEntities.kt` precedent) — all four entities in `vreader.db`:
  ```kotlin
  @Entity(tableName = "search_sections",
      foreignKeys = [ForeignKey(entity = BookEntity::class, parentColumns = ["fingerprintKey"],
          childColumns = ["bookKey"], onDelete = ForeignKey.CASCADE)],
      indices = [Index("bookKey")])
  data class SearchSectionEntity(
      @PrimaryKey(autoGenerate = true) val id: Long = 0,
      val bookKey: String,
      val sectionIndex: Int,       // per-book reading-order/section index (chapter attribution + tie-break)
      val chunkOrdinal: Int,       // UNIQUE monotonic ordinal within (bookKey): (resourceIndex, chunkIndex) flattened — see WI-3 chunk identity
      val sectionTitle: String?,   // chapter label for the snippet attribution; null for TXT/MD
      val text: String,            // RAW display text (snippet source)
      val indexedText: String,     // normalized: NFKC + full case fold + diacritic fold + CJK per-char segmented (FTS column)
  )

  @Fts4(contentEntity = SearchSectionEntity::class, tokenizer = FtsOptions.TOKENIZER_UNICODE61)
  @Entity(tableName = "search_sections_fts")
  data class SearchSectionFtsEntity(val indexedText: String)

  /** Which books are indexed, at which extractor version, and whether indexing SETTLED —
   *  the backfill/diff + completeness seam. FK→books CASCADE (both in vreader.db). */
  @Entity(tableName = "search_index_state",
      foreignKeys = [ForeignKey(entity = BookEntity::class, parentColumns = ["fingerprintKey"],
          childColumns = ["bookKey"], onDelete = ForeignKey.CASCADE)])
  data class SearchIndexStateEntity(
      @PrimaryKey val bookKey: String,   // FK → books, CASCADE
      val indexerVersion: Int,
      val indexedAt: Long,
      val status: String,   // "indexed" | "skipped_unsupported" | "failed" — see WI-5.
                            //  SETTLED (counts toward completeness): "indexed" (has text) OR
                            //  "skipped_unsupported" (terminal, honestly metadata-only).
                            //  NON-SETTLED (holds completeness open): a MISSING row (unvisited)
                            //  or "failed" (RETRY marker — still eligible for reindex, NOT a
                            //  suppress-forever sentinel).
  )
  ```
  The FK→`books` CASCADE on `search_sections`, `search_index_state`, AND `search_sections_staging` (same `vreader.db` schema — legal) makes a book delete clean all four tables (see the staging entity's FK below).

- **`SearchStagingEntity` (in `SearchEntities.kt`)** — the bounded-memory extraction buffer (Gate-2 round-2 HIGH — genuine streaming; see §"Streaming extraction & atomic publish") **with an FK→`books` CASCADE (Gate-2 round-3 HIGH — delete-during-indexing correctness):**
  ```kotlin
  @Entity(tableName = "search_sections_staging",
      foreignKeys = [ForeignKey(entity = BookEntity::class, parentColumns = ["fingerprintKey"],
          childColumns = ["bookKey"], onDelete = ForeignKey.CASCADE)],
      indices = [Index("bookKey")])
  data class SearchStagingEntity(
      @PrimaryKey(autoGenerate = true) val id: Long = 0,
      val bookKey: String,
      val sectionIndex: Int,
      val chunkOrdinal: Int,
      val sectionTitle: String?,
      val text: String,
      val indexedText: String,
  )
  ```
  **The FK→`books` CASCADE is required to make deletion-during-indexing coherent (Gate-2 round-3 HIGH).** The coordinator uses `collect` (NOT `collectLatest`), so a book deleted while the coordinator is mid-index is NOT torn down — the extraction runs to completion. Without an FK, its staging rows would survive the delete, and the subsequent `publishBook` would try to `INSERT` FK-constrained rows into `search_sections`/`search_index_state` for a now-deleted `bookKey` → a foreign-key constraint failure; the coordinator's failure handler would then try to write a `failed` state row for the same missing key → a SECOND FK failure. The FK→`books` CASCADE on staging means the delete **also removes the in-flight staging rows**, and the publish/mark path is made **deletion-aware** (see the coordinator's per-book handling below): it detects the parent book is gone and cleanly skips both the publish and the state write rather than crashing. Staging rows are still **not** part of any FTS content table and are invisible to search until the short atomic publish moves them into `search_sections`; staging is always cleared for a `bookKey` before a fresh extract and in the publish transaction.

- **`SearchDao.kt`** — `insertStagingBatch(rows)`, `clearStaging(bookKey)`, `stagingFor(bookKey)`, `deleteSections(bookKey)`, a **first-hit-per-book** matching query (see below), `markIndexed(state)` (`@Upsert`), `indexStates()`, `indexedBookKeys(): List<String>`, a `bookExists(bookKey): Boolean` guard (deletion-aware publish), a completeness helper over **settled** states, an **observable** completeness/state read exposed as a Room `Flow` (drives `textHits`, see below), and a **`@Transaction` `publishBook(bookKey, state, author?)`** that (a) re-checks `bookExists(bookKey)` and no-ops if the parent book was deleted mid-index, else (b) `deleteSections(bookKey)`, (c) copies `search_sections_staging`→`search_sections` for the key, (d) `clearStaging(bookKey)`, (e) `markIndexed(state)`, and (f) for EPUB with a non-null author, `bookDao.backfillAuthorIfNull(bookKey, author)` — all in ONE short commit (§"Streaming extraction & atomic publish"). **No window functions** (minSdk 26 = SQLite 3.18 has no `ROW_NUMBER`).

  **Completeness helper (Gate-2 round-3 HIGH — SETTLED, not `indexed`-only):** `countUnsettledIndexable(): Int` (or the observable `Flow<Boolean>` form) counts books whose `originalFormat` ∈ {epub,txt,md} that lack a **settled** `search_index_state` row — i.e. `LEFT JOIN search_index_state … WHERE books.originalFormat IN ('epub','txt','md') AND (search_index_state.status IS NULL OR search_index_state.status = 'failed')`. `indexComplete = (countUnsettledIndexable() == 0)`. An `indexed` or `skipped_unsupported` row is settled (does not count); a missing row or a `failed` row is unsettled (counts) and keeps `indexComplete = false` until it converges. This is the single source of truth for the definitive-no-results-copy gate.

  **First-hit-per-book grouping happens in SQL BEFORE the global limit (Gate-2 HIGH — one heavily-matching book must not consume all 200 rows and hide other books).** Two-step, both minSdk-26-safe:
  1. `matchingBookKeys(ftsQuery, limit)`: `SELECT DISTINCT s.bookKey FROM search_sections_fts f JOIN search_sections s ON s.id = f.rowid WHERE search_sections_fts MATCH :ftsQuery ORDER BY s.bookKey LIMIT :limit` — the LIMIT (default 200) now bounds the number of **distinct books**, not raw rows, so no single book can crowd others out.
  2. For each returned bookKey, `firstMatchingSection(bookKey, ftsQuery)`: `SELECT s.* FROM search_sections_fts f JOIN search_sections s ON s.id = f.rowid WHERE search_sections_fts MATCH :ftsQuery AND s.bookKey = :bookKey ORDER BY s.sectionIndex ASC, s.chunkOrdinal ASC, s.id ASC LIMIT 1` — a **deterministic** first hit ordered by the unique `(sectionIndex, chunkOrdinal, id)` tuple. Because `chunkOrdinal` is unique within a book (WI-3), ties are impossible and the "first hit" is stable across runs.

### New files — search feature (`android/app/src/main/kotlin/com/vreader/app/search/`)

- **`SearchTextNormalizer.kt`** — pure JVM. **Mirrors the iOS `vreader/Services/Search/SearchTextNormalizer.swift`** (verified — order: NFKC → case fold → diacritic fold), so the Android index and query normalize identically to iOS:
  - `normalize(text): String` = **(1) NFKC** (`java.text.Normalizer.normalize(text, Form.NFKC)` — the iOS `precomposedStringWithCompatibilityMapping` analog: folds full-width→half-width `０→0 Ａ→A`, ligatures `ﬁ→fi`) → **(2) full Unicode case folding** via **`android.icu.lang.UCharacter.foldCase(str, UCharacter.FOLD_CASE_DEFAULT)`** (Gate-2 round-2 MEDIUM — see below) → **(3) diacritic folding** (NFD decompose then strip `\p{Mn}` combining marks — the iOS `.diacriticInsensitive` analog). The NFKC-first / diacritic-last order matches iOS exactly.
  - **Why `UCharacter.foldCase`, NOT `lowercase(Locale.ROOT)` (Gate-2 round-2 MEDIUM).** `lowercase` is a locale-aware *lowercasing* transform, not Unicode **case folding**. Lowercasing leaves several classes of case-variant unmatched: German `ß` does not lowercase to `ss` (it stays `ß`, while a user typing "strasse" normalizes to `strasse`), the Greek final sigma `ς` and medial sigma `σ` do not unify under lowercasing, and various Cherokee / Deseret / titlecase forms are missed. **Unicode case folding** (the operation FTS/search engines use for case-insensitive matching) canonicalizes all of these: `ß`→`ss`, `ς`/`σ`→`σ`, Cherokee case variants unify (see the Cherokee note below), etc. `android.icu.lang.UCharacter.foldCase(String, UCharacter.FOLD_CASE_DEFAULT)` is the platform case-folding primitive; it is **API 24+** (`android.icu` is the bundled ICU4J), comfortably below this module's **minSdk 26** (verified `app/build.gradle.kts` line 30), so no desugaring or guard is needed. It is locale-independent by construction (folding, not locale casing), which preserves the iOS "Turkish-İ is NOT special-cased" behavior (iOS uses `.caseInsensitive` with `locale: nil`). `FOLD_CASE_DEFAULT` (not `FOLD_CASE_EXCLUDE_SPECIAL_I`) is chosen so dotted/dotless-I fold the default Unicode way, matching iOS's locale-nil case-insensitive fold.
  - **Cherokee folds to its UPPERCASE canonical form (Gate-2 round-3 MEDIUM — NOT "upper→lower").** Cherokee is the well-known exception to the usual "case folding lowercases" intuition: because Cherokee lowercase letters were encoded *after* the uppercase ones, Unicode's stability policy makes the **default full case fold map Cherokee to its historical UPPERCASE representatives**, not to lowercase (verified against the Unicode `CaseFolding.txt` "full" mappings for `U+13A0…`/`U+AB70…`). So the invariant to assert is: an upper-case Cherokee string and its lower-case counterpart **fold to the SAME string**, and that common form is the **UPPERCASE** canonical representative. Both index and query paths run the identical `foldCase`, so an upper-Cherokee query still matches a lower-Cherokee book (and vice-versa) — the parity is what matters; the canonical form just happens to be upper. Wording is corrected everywhere in this plan to "upper+lower Cherokee fold IDENTICALLY (to the uppercase canonical form)", never "Cherokee upper→lower".
  - `segmentCJK(text): String` = insert a space around each CJK code point so unicode61 tokenizes ideographs individually. **Code-point (not char) iteration** so surrogate pairs (non-BMP Han, CJK Ext B+ `U+20000–U+2FA1F`) are never split.
  - `isCjk(codePoint: Int): Boolean` covering the SAME ranges as iOS `isCJKCharacter`: CJK Unified `U+4E00–U+9FFF`, **Ext A `U+3400–U+4DBF`**, **Ext B+ `U+20000–U+2FA1F`**, **Compatibility Ideographs `U+F900–U+FAFF`**, **Hangul Syllables `U+AC00–U+D7AF`**, **Hangul Jamo `U+1100–U+11FF`**, **Hangul Compatibility Jamo `U+3130–U+318F`**, **Katakana `U+30A0–U+30FF`**, **Halfwidth Katakana `U+FF65–U+FF9F`**, **Hiragana `U+3040–U+309F`**.
  - The SAME `normalize` (NFKC → `foldCase` → diacritic-strip) + `segmentCJK` pipeline runs on BOTH the index path (`indexedText`) AND the query path (`SearchQueryBuilder`) — Gate-2 MEDIUM: index/query normalization parity is what makes composed/decomposed accents, ligatures, full-width Latin, half-width kana, Hangul/Jamo, AND full-case-fold pairs (ß↔ss, final sigma, Cherokee) actually match.

The coordinator calls `sink.flushRemaining()` exactly once after `extract()` returns `Success` and before `publishBook`, guaranteeing the partial last batch is written. ### Streaming extraction & atomic publish (binding — Gate-2 round-2 HIGH + round-3 MEDIUM/HIGH)

The v2 plan's "chunked transactions" wording contradicted the single atomic `reindexBook` transaction, and `ExtractedBookText.sections: List` re-materialized the whole book. Both are resolved by a **two-phase pipeline** that is streaming during extraction (EPUB) and atomic only at publish:

1. **Extract → staging, in bounded-memory batches (NOT one transaction).** The extractor STREAMS each finished section to a `SectionSink`; the coordinator's sink accumulates a small batch (e.g. 32 sections) and flushes it via `searchDao.insertStagingBatch(...)`, then drops the batch. For EPUB, at most one batch of section text plus one in-progress section is resident — memory is O(batch), not O(book). (TXT/MD hold the decoded book String — the accepted existing reader bound, per the extractor note; the sink still batches staging writes.) Staging rows are invisible to search (not in the FTS content table). Each staging insert is its own small write; there is deliberately **no** long-held transaction wrapping the whole extraction.
2. **Flush the partial last batch (Gate-2 round-3 MEDIUM).** After `extract()` returns `Success`, the coordinator calls `sink.flushRemaining()` exactly once so the buffered-but-unflushed tail (`sections mod batchSize`, and the whole book when `sections < batchSize`) is written to staging. Without this, a book with fewer sections than one batch would stage ZERO rows and every book would lose its remainder. Tested at 1, N−1, N, N+1 sections.
3. **Publish → ONE short atomic transaction.** After the flush, `searchDao.publishBook(bookKey, state, author)` runs a single `@Transaction` that: re-checks `bookExists(bookKey)` (no-op if the book was deleted mid-index) → `deleteSections(bookKey)` (clear a prior index) → copy `search_sections_staging`→`search_sections` for the key (an `INSERT INTO search_sections (…) SELECT … FROM search_sections_staging WHERE bookKey = :key`, which also populates `search_sections_fts` via Room's content-table triggers) → `clearStaging(bookKey)` → `markIndexed(state)` → EPUB `backfillAuthorIfNull(bookKey, author)`. This transaction touches only already-staged rows + a few metadata rows, so it is short even for a large book — it flips visibility atomically without holding a write lock across the slow extraction.
4. **Cancellation / deletion leaves staging invisible (Gate-2 round-3 HIGH).** A cancel/crash mid-extraction leaves only staging rows (never searched) and NO `search_index_state` row for the key, so the book stays "unindexed" and the coordinator re-extracts it next launch. A **delete** mid-extraction (the `collect` window) triggers the FK→`books` CASCADE, which removes the in-flight staging rows; the `bookExists` guard in `publishBook`/mark then no-ops, so no orphan insert and no double-FK-failure occurs. The coordinator `clearStaging(bookKey)` at the start of each attempt and on any `Unsupported`/`Failed` outcome, and the publish transaction clears staging as its last index step, so staging never accumulates across runs.
5. **`close()` guaranteed in `finally`.** The EPUB extractor's `publication.close()` is in a `finally` on every path (success, unsupported, exception, cancellation) — the leak class the round-1 fix already closed, re-affirmed here because the sink now spans the open publication.

This reconciles "streaming" (phase 1, bounded memory for EPUB) with "atomic" (phase 3, the short publish) — they describe different phases, not a contradiction.

### Coordinator lifecycle (binding — Gate-2 HIGH)

- **Eagerly started, exactly once.** `AppContainer` does NOT expose the coordinator as an un-dereferenced `by lazy` (a lazy nothing touches never starts). `VReaderApp.onCreate` calls `appContainer.startSearchIndexing()` once; the method is **idempotent** (guarded by an `AtomicBoolean`/single-assignment `Job`) so a second call is a no-op and cannot spawn a competing collector.

- **Serialized work** through a single `Mutex` (or a single-consumer channel/actor) so only one book indexes at a time regardless of how fast the library Flow emits.

## 3. Prior art / project precedent / rejected alternatives

**Prior art**: iOS `LibraryContainerModel.swift` (`matchesQuery` metadata semantics, verified); iOS `Services/Search/` (`SearchTextNormalizer` NFKC→fold→diacritic → our normalizer 1:1 with `foldCase` in place of `lowercase`, `SearchTokenizer`/`SearchQueryExecutor` FTS-escape + snippet → our query/snippet builders, `BackgroundIndexingCoordinator` serial-queue + rethrow-cancellation → `SearchIndexCoordinator`, `SearchViewModel` debounce); the `AnnotationDao.upsertHighlight` insert-if-absent-then-update-in-@Transaction idiom (verified lines 100-135) → the author-preserving `upsertPreservingAuthor`; #127 plan+impl (entity/DAO/repository layering, `SheetRoute`/`SheetRouteSaver` saveable routing, migration + exported-schema + Robolectric round-trip discipline, backup parity WI shape, rule-51 "omit undepicted states", the `WebDavRoundTripConnectedTest` live round-trip); migration precedents `MIGRATION_1_2`…`MIGRATION_4_5` (v5 current, verified) + `VReaderDatabaseMigrationTest`; `ReaderSettingsStore`/`OpdsSourceStore`/`AiProviderStore` DataStore + `noBackupFilesDir` (verified `AppContainer.readerSettingsDataStore`, VReaderApp.kt lines 58-62); `TxtDecoder`/`TxtDocument`; `BookOpener.open`/`readMetadata` (caller-owns-close contract, verified); the WebDAV materializing-backup (`backup/WebDavBackupService.kt` + `RestoreImporter.kt`) as the (not-yet-user-wired) cross-device backup mechanism.

**Rejected alternatives**:
1. **FTS4 ICU tokenizer for CJK** — not guaranteed present in Robolectric/OEM SQLite and baked into schema (no runtime fallback). Instead: unicode61 + our own pre-normalization (NFKC + full case fold + per-char CJK segmentation), identical to the iOS pipeline.
2. **FTS5** — Room has no FTS5 annotation support; not guaranteed at minSdk 26. (The "FTS5" string in the designs is iOS-sheet helper copy.)
3. **Plain `LIKE '%q%'` corpus scan** — linear scan per keystroke scales badly. Kept as the token-aware *snippet* strategy only (one matched section, not the corpus).
4. **On-demand extraction per query** — unusable; import-time indexing amortizes it (content-addressed identity means an index never goes stale for a key).
5. **Indexing inside `BookImporter`** — slows import, misses backfill of already-imported/restored books; a coordinator observing the library Flow covers all three. (BookImporter is still touched — but only for the author-preserving upsert, not for indexing.)
6. **Whole-row `@Upsert` on import once `author` exists** — REJECTED (Gate-2 CRITICAL): it null-clobbers a backfilled/restored author on every duplicate import. Replaced with the atomic partial `upsertPreservingAuthor`.
7. **`collectLatest` on the library Flow / a lazy-but-never-started coordinator / a persist-current failure sentinel** — all REJECTED (Gate-2 HIGH): `collectLatest` tears down an in-flight index mid-write; a never-dereferenced lazy never starts; a persist-current sentinel suppresses retries forever. Replaced with eager idempotent start + `collect` + Mutex + a retryable `failed` state.
8. **One-shot `List` for `textHits`** — REJECTED (Gate-2 HIGH): it never re-runs when indexing completes, contradicting "in-text hits appear automatically." Replaced with an observable Room `Flow`.
9. **`LIMIT 200` raw rows before Kotlin grouping** — REJECTED (Gate-2 HIGH): one heavily-matching book eats all 200 rows and hides others. Replaced with SQL first-hit-per-book (distinct-bookKey limit + per-book min-ordinal section).
10. **Raw-literal snippet lookup** — REJECTED (Gate-2 MEDIUM): normalization means many valid FTS matches have no literal raw substring. Replaced with token-aware ranges from the query layer.
11. **A dedicated `search-index.db` database to make an Auto-Backup exclusion table-scoped** — REJECTED (Gate-2 round-2 CRITICAL): SQLite forbids the required cross-schema FK to `books`, a Room `@Transaction` can't span two DB instances (breaks the atomic sections+state+author publish), and it contradicted WI-4 which still put the tables in `VReaderDatabase`. Replaced with ONE `vreader.db` holding all search tables.
12. **Materialized `ExtractedBookText.sections: List` + "chunked transactions"** — REJECTED (Gate-2 round-2 HIGH): a `List` return re-materializes the whole book (defeats streaming), and "chunked transactions" contradicted the single atomic publish. Replaced with a streaming `SectionSink` → batched staging inserts → ONE short atomic `publishBook` transaction (§"Streaming extraction & atomic publish").
13. **`lowercase(Locale.ROOT)` for case-insensitive matching** — REJECTED (Gate-2 round-2 MEDIUM): lowercasing is not full Unicode case folding; it misses ß↔ss, Greek final/medial sigma, Cherokee, titlecase forms. Replaced with `android.icu.lang.UCharacter.foldCase(str, FOLD_CASE_DEFAULT)` (API 24, safe below minSdk 26) on BOTH index and query paths, keeping the NFKC-first / diacritic-last order.
14. **Excluding the whole `vreader.db` from Android Auto Backup** — REJECTED (Gate-2 round-3 HIGH, the root of a 2-round flip-flop): incoherent with the codebase. Books live under `filesDir/books` (verified `VReaderApp.kt` line 31), which Auto Backup includes by default; excluding only the DB restores book FILES with no METADATA → empty library + orphaned blobs. No Android WebDAV recovery is wired (verified: `architecture.md` line 583; no `WebDavBackupService` in `AppContainer`), so Auto Backup is the ONLY restore today and only works if DB + `filesDir` are backed up together. Replaced with: keep the default Auto Backup (books + metadata restore coherently); the index adds bounded, self-healing (device-local derived) size; revisit an index-only exclusion ONLY if/when Android WebDAV recovery ships AND quota becomes a real problem — and note a table-level exclusion is impossible (Android backup rules are file/folder-granular), so it would require a separate index DB file, which reintroduces the cross-schema-FK problem (alt #11). Not a #128 line item.
15. **Excluding just the "index tables" of `vreader.db` from Auto Backup** — REJECTED (Gate-2 round-3): Android Auto Backup rules operate on files/folders, NOT tables; you cannot exclude some tables of one DB file. Table-level exclusion would require physically splitting the index into a separate DB file (alt #11's cross-schema-FK problem). So there is no partial-DB exclusion; the DB is backed up whole (as now) or would have to be split (rejected).
16. **A staging table with NO foreign key** — REJECTED (Gate-2 round-3 HIGH): with `collect` (not `collectLatest`), a book deleted mid-index leaves surviving staging rows; the subsequent `publishBook` FK-inserts into `search_sections`/`search_index_state` fail, and the failure handler's `failed`-state write FK-fails again. Replaced with an FK→`books` CASCADE on `search_sections_staging` (delete cascades the staging rows) + a `bookExists` guard in publish/mark (deletion-aware no-op).
17. **`SectionSink` with only `emit` (no final flush)** — REJECTED (Gate-2 round-3 MEDIUM): the coordinator's sink buffers into N-sized batches; without a `flushRemaining()` a book with < N sections stages ZERO rows and every book loses its `mod N` tail. Replaced with a `SectionSink.flushRemaining()` the coordinator calls once after `Success` and before `publishBook`; tested at 1, N−1, N, N+1 sections.
18. **Claiming bounded O(batch) memory for ALL formats** — REJECTED (Gate-2 round-3 HIGH): `TxtDecoder.decode` does `file.readBytes()`+`String(...)` and `TxtDocument` retains the whole decoded String (verified), so TXT/MD is O(book-size), not O(batch). Narrowed the bounded claim to EPUB; TXT/MD is documented as the ACCEPTED existing reader bound (it matches what the TXT/MD reader already loads) + budgeted/tested against the real large `.txt`. Streaming charset-detecting decoder = named follow-up (reader-parity-first).
19. **Completeness = every indexable book `indexed`** — REJECTED (Gate-2 round-3 HIGH): a `skipped_unsupported` book (no-content-service EPUB) would never become `indexed`, so `indexComplete` would be `false` FOREVER and the definitive no-results copy would be suppressed permanently. Replaced with completeness over **settled** states: `indexed` OR `skipped_unsupported` both count; only a missing row or a retryable `failed` row holds completeness open.
20. **Cherokee "upper→lower" case-fold expectation** — REJECTED (Gate-2 round-3 MEDIUM): Unicode's stability policy makes the default full case fold map Cherokee to its historical UPPERCASE representatives, not lowercase. The test asserts upper+lower Cherokee fold **identically** to the **UPPERCASE** canonical form (parity is the property that matters); "upper→lower" wording corrected throughout.
21. **Android-only `author` addition to the backup contract** — moot: the field already exists; we only start honoring it.
22. **A separate `SearchActivity`** — the design is a Library-context takeover; in-`MainActivity` saveable route matches the `SheetRoute` precedent.

## 6. Risks + mitigations

1. **FTS4/unicode61 availability under Robolectric/OEM SQLite** — unicode61 compiled into framework + Robolectric SQLite; we avoid ICU tokenizers. Fallback: move `SearchDaoTest` to androidTest. CJK never depends on the tokenizer (pre-segmentation), and normalization matches iOS.
2. **Readium `publication.content()` is `@ExperimentalReadiumApi` AND nullable** — pinned 3.3.0; behind the `BookTextExtractor` seam; **null (no content service) is a typed `Unsupported`, not a crash** (verified via bytecode). Fallback: iterate reading-order resources + strip tags (iOS approach) in the same seam.
3. **Large EPUB extraction memory (Gate-2 round-2 HIGH)** — genuinely bounded for EPUB: stream via `content.iterator()` (never `content.elements()`), emit each section to a `SectionSink` that flushes small batches to the staging table and drops them, then a SHORT atomic `publishBook` swaps staging→sections. At most one batch resident. DB grows ≈ 2× corpus text; verified against the ~18 MB real EPUB at WI-8.
4. **TXT/MD extraction memory is O(book-size), NOT O(batch) (Gate-2 round-3 HIGH)** — `TxtDecoder.decode` reads the whole file and builds a decoded String; `TxtDocument` retains it (verified). This is the **accepted existing reader bound** — indexing a TXT/MD loads exactly what the TXT/MD reader already loads to display it, so it is not a new regression. Budgeted + tested against the real ~14 MB `.txt` at WI-3/WI-8. A streaming charset-detecting decoder for indexing is a named follow-up (reader parity first). The sink still batches staging writes so the DB-write side stays incremental.
5. **Index staleness** — impossible per key (content-addressed identity). Extractor-logic changes handled by `indexerVersion`; a `failed` state is retried, not suppressed.
6. **Author clobber on re-import / restore (Gate-2 CRITICAL)** — atomic `upsertPreservingAuthor` on import (author never in the SET list), the single `applyRestoredMetadata` `COALESCE` on restore (also restoring title/addedAt/lastOpenedAt), `UPDATE … WHERE author IS NULL` backfill in the coordinator; both restore/coordinator orderings tested; the self-latching current-state-beside-null case is closed because the preserving upsert never nulls a set author in the first place.
7. **Cancellation leaving a current state row beside a null author (Gate-2 HIGH)** — the visibility-flipping write is one short `publishBook` transaction (staging swap + state + conditional author); a crash/cancel either commits all or none, and pre-publish work is only invisible staging; staging is cleared on every attempt/outcome; tested.
8. **Deletion during indexing (Gate-2 round-3 HIGH)** — `collect` (not `collectLatest`) lets an in-flight index finish against a possibly-deleted book. The staging FK→`books` CASCADE removes its staging rows on delete, and `publishBook`/mark first check `bookExists` and no-op if the parent is gone, so no orphan `search_sections`/`search_index_state` insert and no double-FK-failure. Deterministically tested (delete between `insertStagingBatch` and `publishBook`).
9. **Partial last batch lost (Gate-2 round-3 MEDIUM)** — `SectionSink.flushRemaining()` drains the buffered tail (and the whole book when `sections < batchSize`); the coordinator calls it once after `Success` before `publishBook`. Tested at 1, N−1, N, N+1 sections.
10. **Snippet highlight on normalized matches (Gate-2 MEDIUM)** — token-aware ranges from the query layer, not a raw-literal lookup; no-locatable-token → no wash rather than a wrong highlight (covers ß→ss expansion matches).
11. **Auto Backup / index size (Gate-2 round-3 HIGH — no exclusion)** — the app keeps its DEFAULT Auto Backup; the search index rides in `vreader.db` (books+metadata restore coherently — the ONLY restore path until Android WebDAV recovery is wired). The index adds bounded size and is device-local **derived** data (self-healing: the coordinator reconciles any stale/partial restored index on first launch via content-addressed identity). Excluding the DB would restore book FILES with no METADATA (empty library + orphaned blobs, since books live under `filesDir/books`). A future index-only exclusion is a dedicated follow-up gated on WebDAV recovery shipping AND a real quota problem — and would require a separate index DB file (table-level exclusion is impossible), reintroducing the cross-schema-FK problem, so it is explicitly out of #128.
12. **Full-case-fold correctness (Gate-2 round-2 MEDIUM + round-3 MEDIUM)** — `UCharacter.foldCase(str, FOLD_CASE_DEFAULT)` (API 24, below minSdk 26) on both index and query paths, NFKC-first/diacritic-last order preserved; regression-tested with ß↔ss, Greek final/medial sigma, and **Cherokee (upper+lower fold IDENTICALLY to the UPPERCASE canonical form — not "upper→lower")**.
13. **Search before indexing completes (Gate-2 HIGH + round-3 HIGH)** — metadata search always live; in-text appears automatically because `textHits` is an observable Flow; the definitive no-results copy is gated on `indexComplete`, which is computed over **settled** states (`indexed`/`skipped_unsupported`) so a no-content-service EPUB does NOT block it forever, while a missing or retryable-`failed` book keeps it honestly open until resolved; no invented progress state (rule 51).
14. **MATCH result explosion / one book hiding others (Gate-2 HIGH)** — SQL first-hit-per-book (distinct-bookKey limit + per-book min-ordinal section) + debounce; a heavily-matching book contributes exactly one row.
15. **Coordinator never starts / competing collectors (Gate-2 HIGH)** — eager idempotent `startSearchIndexing()` from `onCreate`, single process-lifetime `Job`, `collect` not `collectLatest`, Mutex-serialized.
16. **`MainActivity` growth** — keep the route wiring thin (state + two lambdas); logic in `SearchViewModel` (rule 50 file-size discipline).

## 7. Backward compat

- **Existing installs**: v5→v6→v7 purely additive (`ALTER TABLE ADD COLUMN`, new tables/FTS/staging, all in the one `vreader.db`). Migration round-trip tests guard both + the full chain. Existing books get `author = NULL` + no index rows; the coordinator backfills author (EPUB) + text index in the background on first launch — no user action, no data loss. Fresh installs create v7 directly.
- **Author never lost after this ships**: a duplicate import or a restore of a book whose author is already set preserves it (`upsertPreservingAuthor` / `applyRestoredMetadata` COALESCE), so the new column is durable across the operations that previously would have nulled it. Restore now also correctly re-applies title/addedAt/lastOpenedAt via the single `applyRestoredMetadata` update.
- **Backup format**: **no contract change** — `BackupLibraryEntry.author` has existed since #113 on both platforms; `MANIFEST_SCHEMA_VERSION` stays 1. Old Android backups restore null; new Android backups populate the field; old Android builds ignore it on restore; iOS already consumes it. Null authors omitted (`explicitNulls=false`) → byte-identical manifest for a no-author library (byte-stability tests in WI-2).
- **Android Auto Backup: UNCHANGED (Gate-2 round-3 HIGH — the v3 exclusion is dropped).** This feature adds **no** Auto-Backup config — the app keeps its default `allowBackup=true` with no `dataExtractionRules`/`fullBackupContent`. Books (under `filesDir/books`) + `vreader.db` (metadata + the new search index) continue to back up **together**, which is the only coherent behavior because (a) no Android WebDAV recovery is wired yet, so Auto Backup is the ONLY restore path, and (b) excluding the DB would restore book files without metadata (empty library + orphaned blobs). The search index + staging are device-local derived data; if a restore carries a stale/partial index, the coordinator reconciles it on first launch (content-addressed identity). Recent searches live in `noBackupFilesDir` DataStore and are excluded implicitly (unchanged). Index size is a bounded, revisit-later concern (§"Auto Backup"), not a restore-correctness one.
- **No behavior change** beyond the new Search pill, the designed author subtitle appearing as authors are backfilled, and in-text results appearing as indexing completes. Auto Backup behavior is unchanged from today's default.
