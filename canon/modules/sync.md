# Module — sync

## Purpose

Scaffolding for cross-device CloudKit sync — conflict resolution, tombstones, an outbound queue, change-token persistence, CKRecord mapping, and status UI. **The whole subsystem is dormant**: `SyncService`'s mutating/coordination entry points are guarded by `FeatureFlags.sync`, whose default is `false` in ALL environments (`FeatureFlags.defaultValue(for: .sync, ...)` in `vreader/Services/FeatureFlags.swift`) — `fileAvailability(for:)` is the one unguarded read, always returning tracked-or-`.metadataOnly` state — and the production `CloudKitClient` is an explicit stub that throws `SyncError.syncDisabled` from every method. The user-facing backup path is WebDAV, not this module (see [[Module — backup and WebDAV]]; `docs/features.md` row 10 marks iCloud backup WONT DO). Nothing in the module is wired into the running app today — `NSUKVSBridge` (the preference mirror) has no production call site either, same as the rest; what exists is unit-tested pure logic sitting in the compiled binary, inert.

## Key files and types

All under `vreader/Services/Sync/` unless noted:
- `SyncService.swift` — `actor SyncService`. The mutating/coordination entry points start with `guard featureFlags.sync else { return .disabled }` (or plain return): `syncMetadata(for:)` is a V2 coordination stub; `requestFileDownload(bookFingerprintKey:)` drives the state machine and returns `.queued`; `recordTombstone` / `purgeStaleTombstones` delegate to `DurableTombstoneStore`. `fileAvailability(for:)` is the exception — it has no feature-flag guard and just reads `fileStates[bookFingerprintKey] ?? .metadataOnly`, so it returns real (or default `.metadataOnly`) state regardless of whether sync is enabled. `static let tombstoneRetentionSeconds: TimeInterval = 30 * 24 * 3600` (30 days).
- `SyncTypes.swift` — `FileAvailability` (6 states: `metadataOnly / queuedDownload / downloading / available / failed / stale`), `FileAvailabilityEvent`, `SyncConflictResult` (`useLocal/useRemote`), `SyncSessionResult` (`append/skip`), `SyncOperationResult`, `SyncStatus` (`disabled/idle/syncing/error/offline`), `TombstoneEntityType` (`bookmark/highlight/annotation`), `Tombstone`, `FileManifest`, `SyncError`.
- `FileAvailabilityStateMachine.swift` — pure `transition(from:event:)` implementing 7 valid transitions ("plan Section 4.3"); invalid combos are no-ops; `canOpenReader` is true only for `.available`. NOTE: this 6-state `FileAvailability` is a separate, older mechanism from feature #47's persisted `BookFileState` (`local/remoteOnly/downloading/failed/missingRemote` in `vreader/Models/BookFileState.swift`) that the backup module actually uses.
- `SyncConflictResolver.swift` — pure-function merges ("plan Section 9.4"): position = LWW by `updatedAt` with lexicographic deviceId tie-break (larger wins); bookmark = tombstone-aware LWW keeping the earliest `createdAt`; highlight/annotation = tombstone-aware LWW; library metadata = user-edited beats extracted, then newer wins; file manifest = higher `manifestVersion` wins, checksum mismatch at equal version sets `requiresStale`; reading sessions = append-only idempotent (`skip` when the session id already exists). Shared `resolveTombstoneAwareLWW` gives the tombstone precedence on equal timestamps (delete bias).
- `TombstoneStore.swift` — `protocol TombstonePersisting` + `InMemoryTombstoneStore` (idempotent adds keep the later `deletedAt`).
- `DurableTombstoneStore.swift` — `actor`, JSON file `tombstones.json` (default directory Application Support/Sync), lazy load, write-through with `.atomic`, corrupt file recovers to empty; `addTombstone` throws on write failure (audit fix).
- `SyncOutboundQueue.swift` — `actor`; FIFO, dedupe by (recordType, recordID) where a re-enqueue mints a NEW UUID so an in-flight flush snapshot can't delete the newer version (audit fix: flush race); `markCompletedBatch(ids:)` removes only the snapshot; `clearAll()` for the disable-sync flow. In-memory backing; SwiftData backing deferred.
- `SyncPipeline.swift` — `actor` orchestrating enqueue → `flush()` (snapshot IDs before the `await client.saveRecords`, mark only those completed) → `fetchChanges(zoneID:)` (an `isFetching` bool rejects overlapping fetches; the change token is saved only after a successful fetch — audit fix: token race) → `processInbound` (Phase 1 stub that just counts). Also `createZone` / `subscribe` pass-throughs.
- `CloudKitClient.swift` — `protocol CloudKitClientProtocol` (saveRecords / fetchChanges / createZone / subscribe) + lightweight `SyncOutboundRecord` / `SyncInboundRecord` (String-keyed fields, avoiding `Any` Sendable issues) / `SyncFetchResult`. Production `CloudKitClient` declares `containerID = "iCloud.com.vreader.app"` but throws `SyncError.syncDisabled` everywhere — "full implementation deferred to WI-000 (entitlements spike)".
- `CloudKitRecordMapper.swift` — bidirectional CKRecord mapping for all 8 record types: `VRBook`, `VRReadingPosition`, `VRBookmark`, `VRHighlight`, `VRAnnotation`, `VRReadingSession`, `VRBookSource`, `VRReplacementRule`. Booleans as Int64 0/1 (CloudKit has no Bool), Locators as JSON strings, record name = the type's unique key (fingerprintKey, bookmarkId, …); decode returns nil on missing required fields.
- `SyncRecordDTOs.swift` — the mapper's Sendable DTOs (`SyncBookRecord`, `SyncCKBookmarkRecord` etc. — `CK`-infixed names avoid collision with the resolver's conflict-field records).
- `ChangeTokenStore.swift` — per-zone CK server change tokens in UserDefaults under `"ck_changeToken_" + zone`; `@unchecked Sendable` final class.
- `DeviceIdentity.swift` — stable device UUID in Keychain (service `com.vreader.sync.identity`, account `com.vreader.deviceId`, `kSecAttrAccessibleAfterFirstUnlock` so background sync can read it; survives reinstall). Thread-safe via the atomic `SecItemAdd`-then-read-on-`errSecDuplicateItem` pattern.
- `NSUKVSBridge.swift` — `@MainActor` bridge UserDefaults ↔ `NSUbiquitousKeyValueStore` for exactly 5 keys (`librarySortOrder→library.sortOrder`, `libraryViewMode→library.viewMode`, `readerTheme→reader.theme`, `aiEnabled→ai.enabled`, `syncSchemaVersion→schemaVersion`); `pullAll` skips nil cloud values, `handleExternalChange` propagates cloud deletions by removing the local key (audit fix). Test seam: `protocol CloudKeyValueStore`.
- `SyncStatusMonitor.swift` — `@Observable @MainActor` status/lastSyncDate/pendingChangesCount holder for UI.

Views (`vreader/Views/Sync/`): `SyncStatusView.swift` — compact toolbar badge, hidden entirely when `monitor.status == .disabled`; `FileAvailabilityBadge.swift` — per-book overlay with Retry for `.failed`/`.stale`, hidden when `.available`. Both use `AccessibilityFormatters` labels.

## Dependencies

Internal: `FeatureFlags` (the gate), `KeychainService` conventions (DeviceIdentity uses raw Security APIs deliberately, decoupled from credential storage), SwiftUI/Observation for the monitor and views. External: CloudKit (mapper only), Security, Foundation. It does NOT touch `PersistenceActor` yet — apply-to-store logic is explicitly deferred (`SyncPipeline.processInbound` stub).

## Data flow (as designed, mostly latent)

Local change → `SyncPipeline.enqueue(recordType:recordID:recordData:)` → `SyncOutboundQueue` (dedup) → `flush()` batches to `CloudKitClientProtocol.saveRecords`. Inbound: push notification → `fetchChanges(zoneID:)` with the stored token → `processInbound` (future: resolve via `SyncConflictResolver`, apply via PersistenceActor). Wiring today: `VReaderApp.swift` creates a `SyncStatusMonitor` ONLY in `#if DEBUG` and only when `config.enableSync` is set (the `--enable-sync` launch argument, `VReaderApp.swift` lines 336–343 and 703); Release hard-codes `syncMonitor = nil`, so `SyncStatusView` never renders in production. `docs/architecture.md` lists `SyncService` as "CloudKit (feature-flagged)" — accurate.

## Concurrency

`SyncService`, `SyncPipeline`, `SyncOutboundQueue`, `DurableTombstoneStore` are actors; the resolver and state machine are pure Sendable structs; monitor and bridge are `@MainActor`. The queue's new-UUID-on-re-enqueue plus the pipeline's snapshot-ID flush is the documented fix for the "flush loses records re-enqueued during the await" race; `isFetching` + save-token-only-on-success is the fix for the change-token race.

`SyncOutboundQueue` (`vreader/Services/Sync/SyncOutboundQueue.swift:48`) and `DurableTombstoneStore` (`vreader/Services/Sync/DurableTombstoneStore.swift:56`) are each independent actor-isolated persistence boundaries in their own right, distinct from the two mechanically-tracked actors (`PersistenceActor`, `ChapterTranslationStore`) that own SwiftData writes elsewhere in the app. `SyncOutboundQueue` owns an in-memory FIFO (`[SyncOutboundQueueItem]`, SwiftData backing explicitly deferred); `DurableTombstoneStore` owns the `tombstones.json` file, lazily loaded and written through on every mutation.

## Edge cases and invariants

- The mutating/coordination entry points (`syncMetadata`, `requestFileDownload`, `recordTombstone`, `purgeStaleTombstones`) degrade to a typed `.disabled`/no-op when the flag is off — tests can construct standalone `FeatureFlags(environment:)` instances to flip it. `fileAvailability(for:)` is unguarded and keeps returning real/default state (`.metadataOnly` when untracked) whether or not sync is enabled.
- Tombstone adds are idempotent, keeping the later `deletedAt`; equal-timestamp conflicts bias toward the delete.
- 30-day tombstone retention is enforced at the `SyncService` call site, not inside the stores.
- `DurableTombstoneStore` never crashes on corrupt/empty JSON (returns empty, records `lastError`).
- `CloudKitRecordMapper` decode functions return nil rather than fabricate defaults for missing required fields.
- `NSUKVSBridge.pushAll` writes nil for missing local values to clear stale cloud entries, while `pullAll` never overwrites local with nothing — asymmetric on purpose.

## History

The module predates the current tracker discipline: its comments cite "the sync plan" Sections 4.3/9.4 and generic "audit fix" markers (flush race, token race, tombstone write-throwing, cloud-deletion propagation) rather than bug #N rows. `dev-docs/plans/20260322-1600-icloud-backup.md` is the era's plan artifact. Feature #47 later built the *shipping* per-book file-state mechanism (`BookFileState` + `LazyDownloadCoordinator`) in the Backup module instead of activating this one, and `docs/features.md` rows 298/369 record the explicit decision to stay on WebDAV with "No CloudKit migration". Full test coverage exists at `vreaderTests/Services/Sync/` (11 test files incl. `SyncConflictResolverTests`, `SyncPipelineTests`, `NSUKVSBridgeTests`, `DurableTombstoneStoreTests`).
